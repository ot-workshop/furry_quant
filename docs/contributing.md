# 成员职责与交付流程

## 分工与入口

任务、验收条件与阻塞归属在 Raft 的 #福瑞量化 任务会话维护；代码、命令和持续文档在本仓库迭代，不把代理电脑上的绝对路径当作跨机交付。

| 负责人 | 职责 |
| --- | --- |
| 量化ceo | 产品目标、优先级、拆分协调，与 CTO 商定范围，核实证据后决定并执行 PR 合并。 |
| 量化cto | 技术方向与独立 PR 审批，尽早审架构、耦合、功能、代码质量及前端整体效果。 |
| 量化牛马、量化哈基米 | 代码实现与修复；牛马另负责 Linux 发布、版本核对与回滚，哈基米先负责 workflow 适配。 |
| 量化测试 | 测试方案/代码、固定 PR workflow 检查、独立回归、UI 逻辑验收与部署后冒烟。 |
| 量化美工 | 交互与视觉方案，桌面/手机、图表可读性和视觉验收；实现交研发。 |
| 量化文档 | 核对已有功能与使用方法，维护测试、发布、回滚和变更说明；随每个 PR 更新。 |
| Cindy | 成员分工索引与协作入口，反馈权限或消息未送达。 |
| Stamp | 仓库身份、推送/PR/检查与事件服务；自动状态不代替人的技术审批。 |

## 从目标到发布

1. CEO 给出目标、范围、验收条件和负责人；CTO 尽早核方向，美工提前审涉及用户的交互。已有任务不另开冲突实现。
2. 实现、测试与文档在各自分支并行。共享接口、数据口径、环境和失败路径先对齐；提交包含可复现输入及必要测试，不把未验证功能写成已支持。
3. 发布固定 PR head 和 base，说明改动、测试结果、跳过/未验部分和风险。测试独立核必要 workflow、真实 PostgreSQL 与 UI 路径；每次新提交重核相关检查。命令和证据要求见[测试指南](testing.md)。
4. CTO 对固定版本独立批准，CEO 核验最新证据后最终合并。Stamp 的 READY、旧头批准、单项通过及自动化检查都不是整批已验收或已部署的证明。
5. 合并后核对实际提交与文件树，再验证对应提交的发布检查、镜像完整 SHA 标签和 digest。牛马使用该产物部署 Linux，量化测试做线上冒烟，文档登记版本与变化。产物未验收或发布目标未固定时不追随移动的 `master` 标签。
6. 失败由当前执行人报告具体失败阶段和证据；实现问题交实现人，测试/环境问题交测试负责人或牛马，发布取舍与回滚决定交 CEO、技术兼容性由 CTO 核。备份、回滚和临时资源清理随交付闭环。

## 每个 PR 的文档检查

- 新增或调整页面、API、参数、数据前置条件时，更新 README 与对应专题文档，包含一条正常使用路径及错误/空状态。
- 指标、因子、缺失处理或冻结规则变化时，写清真实 0、缺失与未知，更新方法限制及旧结果兼容边界；不把历史结果默认为已重算。
- workflow、依赖、环境变量、命令或部署文件变化时，同步测试与运维文档；明确当前支持的完整提交、镜像命名、digest、迁移和回滚条件。
- 验证记录包括 PR/head/base/检出 SHA、输入/数据版本、命令、退出码与跳过原因、run/产物链接、UI 环境及清理结论。未完成项给出负责人和完成条件，不用空白表示通过。

发布记录至少写：合并提交、发布 run、镜像 digest、部署时间、部署前备份与校验、原镜像回滚点、迁移状态、健康与版本核对、线上冒烟、残留资源及下一负责人。PR 说明可以记录本次行为变化，发布记录对应实际部署事实；不要把计划部署写成已上线。

每个可核验的小目标完成后，由 CEO 向用户给出入口、样例、版本及限制。实质版本更新由 CEO 组织发布 GitHub Release，记录变更、测试、完整提交、镜像 digest 和部署状态；计划版本号不等于已经发布的 Release。
