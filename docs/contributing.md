# 贡献与交付流程

## 分工与入口

贡献前在公开 Issue 或 PR 中说明目标、范围、验收条件和当前负责人；代码、命令与持续文档在本仓库迭代。交付使用仓库相对路径和可复现命令，避免依赖某台电脑的本地文件。

| 职责 | 工作范围 |
| --- | --- |
| 产品与合并维护 | 明确产品目标、优先级与范围，核实评审和测试证据后决定并执行 PR 合并与版本发布。 |
| 技术评审 | 独立审核架构、耦合、功能、代码质量和兼容性，批准固定版本的技术方案与实现。 |
| 研发与运维 | 实现和修复代码、维护 workflow，按已批准方案执行 Linux 部署、版本核对与回滚。 |
| 测试 | 维护测试方案与用例，核固定 PR 的检查、独立回归、UI 逻辑和部署后冒烟。 |
| 设计 | 审核交互、信息层级、图表可读性及桌面/手机效果，与研发协作实现。 |
| 文档 | 核对已有功能与使用方法，随 PR 更新测试、发布、回滚和变更说明。 |

## 从目标到发布

1. 产品维护者给出目标、范围、验收条件和负责人；技术评审者尽早核方向，设计参与用户交互审查。已有任务不另开冲突实现。
2. 实现、测试与文档在各自分支并行。共享接口、数据口径、环境和失败路径先对齐；提交包含可复现输入及必要测试，不把未验证功能写成已支持。
3. 发布固定 PR head 和 base，说明改动、测试结果、跳过/未验部分和风险。测试独立核必要 workflow、真实 PostgreSQL 与 UI 路径；每次新提交重核相关检查。命令和证据要求见[测试指南](testing.md)。
4. 技术评审者对固定版本独立批准，合并维护者核验最新证据后最终合并。自动化检查、旧头批准及单项通过都不是整批已验收或已部署的证明。
5. 合并后核对实际提交与文件树，再验证对应提交的发布检查、镜像完整 SHA 标签和 digest。运维使用该产物部署 Linux，测试做线上冒烟，文档登记版本与变化。产物未验收或发布目标未固定时不追随移动的 `master` 标签。
6. 失败由当前执行人报告具体阶段和证据；实现问题交研发，测试/环境问题交测试或运维，发布取舍与回滚决定交发布维护者、技术兼容性由评审者核对。备份、回滚和临时资源清理随交付闭环。

## 每个 PR 的文档检查

- 新增或调整页面、API、参数、数据前置条件时，更新 README 与对应专题文档，包含一条正常使用路径及错误/空状态。
- 指标、因子、缺失处理或冻结规则变化时，写清真实 0、缺失与未知，更新方法限制及旧结果兼容边界；不把历史结果默认为已重算。
- workflow、依赖、环境变量、命令或部署文件变化时，同步测试与运维文档；明确当前支持的完整提交、镜像命名、digest、迁移和回滚条件。
- 验证记录包括 PR/head/base/检出 SHA、输入/数据版本、命令、退出码与跳过原因、run/产物链接、UI 环境及清理结论。未完成项给出负责人和完成条件，不用空白表示通过。

发布记录至少写：合并提交、发布 run、镜像 digest、部署时间、部署前备份与校验、原镜像回滚点、迁移状态、健康与版本核对、线上冒烟、残留资源及下一负责人。PR 说明可以记录本次行为变化，发布记录对应实际部署事实；不要把计划部署写成已上线。

每个可核验的小目标完成后，维护者向用户给出入口、样例、版本及限制。实质版本更新通过 GitHub Release 记录变更、测试、完整提交、镜像 digest 和部署状态；计划版本号不等于已经发布的 Release。

## 数据库迁移

新增迁移时，以下位置必须一起更新，漏一处 CI 的启动检查或 `backup-restore` 作业会失败：

- `alembic/versions/<新版本>.py`：新迁移文件，`down_revision` 指向当前头；
- `src/finance_quant/persistence/database.py` 的 `SCHEMA_REVISION`：应用只接受与其完全相等的库迁移版本，不匹配即拒绝启动；
- `scripts/check_compose_startup.py` 的 `HEAD_REVISION`，以及该文件内 startup 探针迁移里 `down_revision` 的**字面量**（探针文本不是 f-string，写常量名会得到 `NameError`）。

迁移只写增量、保证新库 `upgrade head` 与既有库升级都能跑通；涉及既有表结构变化的迁移要在 PR 说明里写清回滚口径，不能沿用“只新增表时可降级”的默认说法。部署顺序与回滚条件见[运维](operations.md#含新迁移的版本)。
